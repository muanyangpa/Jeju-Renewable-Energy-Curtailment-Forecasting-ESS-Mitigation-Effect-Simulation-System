## 실행

```bash
pip install -r requirements.txt

# 0) 원본 공공데이터 CSV 위치 지정 (기본값: ai_server/data/raw)
export DATA_DIR=/path/to/원본CSV폴더

# 1) 모델 학습 (최초 1회, 또는 데이터 갱신 시)
python -m app.training.train_converter
python -m app.training.train_classifier
python -m app.training.train_curtailment_regressor   # 풍력 전용, 2단계(분류->조건부 회귀)

# 2) 검증 (서비스와 무관, 결과는 models/*.csv)
python -m app.training.evaluate_pipeline             # 날씨→컨버터→분류기 서비스 경로 성능
python -m app.training.validate_demand_blockcv       # 풍력 수요피처 6블록 교차검증

# 3) 점검 후 서버 기동
python smoke_test.py
uvicorn app.main:app --reload --port 8000
```

>
> | 경로 | 이전 | 현재 |
> |---|---|---|
> | 태양광 | `classifier_solar` | `classifier_solar_calibrated` |
> | 풍력 + 수요예측 | `classifier_wind_demand` | `classifier_wind_demand_calibrated` |
> | 풍력, 수요 생략 | `classifier_wind` | `classifier_wind_calibrated` |
>
> **`curtailment_probability`의 크기도 함께 바뀌었습니다** — 고정 임계값(0.5 등)을 쓰지 마세요.
> 아래 '운영 임계값' 참고.

**요청**
```json
{
  "energy_type": "solar" | "wind",
  "region": "남원읍",
  "target_date": "2026-09-22",
  "weather": [ {"hour": 1, "solar_rad": 0.0, "temp": 18.2, "cloud": 4.0, "wind_speed": 5.1}, ... 24개 ... ],
  "demand_forecast_mw": [600.1, ...] // 24개, 풍력 전용(선택)
}
```

**검증 책임 분담 (09장 리스크 대응 그대로)**
- Backend: `weather` 필드 존재 여부·JSON 타입만 확인
- AI 서버(여기): `weather`가 정확히 24개인지, 1~24시가 중복·누락 없이 있는지 최종 검증
  - 위반 시 `422 {"error_code": "INVALID_HOUR_SET", "message": "..."}`
- AI 서버(여기): 발전원별 필수 기상값이 24시간 모두 있는지 검증
  - 태양광: `solar_rad`, `temp`, `cloud` / 풍력: `wind_speed`
  - 위반 시 `422 {"error_code": "MISSING_REQUIRED_FIELD", "message": "..."}`
- Backend는 이 에러코드들을 그대로 릴레이하면 됨 (별도 매핑 불필요)

**응답**
```json
{
  "energy_type": "solar",
  "region": "남원읍",
  "target_date": "2026-09-22",
  "hourly": [
    {"hour": 1, "generation_forecast_mwh": 0.0, "curtailment_probability": 0.02, "expected_curtailment_mwh": null},
    ...
  ],
  "model_used": "classifier_solar_calibrated",  // 확률을 산출한 보정 모델
  "note": "태양광은 ... expected_curtailment_mwh를 제공하지 않습니다 ..."  // 태양광, 또는 풍력에서 수요예측 생략 시
}
```

풍력에서 `demand_forecast_mw`를 생략하면 수요 미포함 모델(`classifier_wind_calibrated`)로 예측하고
`expected_curtailment_mwh`는 null이다(제어량 회귀모델이 수요 피처를 필요로 함).

**중요**: `expected_curtailment_mwh`는 **풍력만** 값이 채워진다. 태양광은 항상 `null`이다 —
전력거래소가 태양광 출력제어량(MWh)을 공식적으로 산정하지 않기 때문(계획서 07장, data.go.kr 메타데이터로
확인됨). 프론트엔드/대시보드에서 태양광에 대해 이 필드를 표시할 때는 반드시 `note` 문구를 함께 노출할 것.

**⚠ ESS 계산에 쓰지 말 것**: `expected_curtailment_mwh`는 `P(제어 발생) × E[제어량|제어 발생]`로
계산한 **기댓값**이다. 총합 추정에는 쓸 수 있으나 개별 시간의 제어량 크기가 아니므로,
`/ess/simulate`의 `hourly_curtailment_mwh`로 그대로 넘기면 흡수율이 크게 과대평가된다
(2023 검증: 실측 36.8% → 87.3%). 자세한 수치는 아래 '제어량 2단계 추정' 및 '알려진 한계' 참고.

### POST /ess/simulate

04장 02번(기본 ESS 시뮬레이션)과 03번(용량 조정 슬라이더)이 공유하는 엔드포인트.

`hourly_curtailment_mwh`에는 **실측 제어량**을 넣는다. `/predict`의 `expected_curtailment_mwh`를
넣으면 안 된다(위 경고 참고).
슬라이더는 `rated_power_mw`만 바꿔가며 이 엔드포인트를 반복 호출하면 된다.

```json
// 요청
{"hourly_curtailment_mwh": [10, 30, 5, 0, 40], "rated_power_mw": 22.5, "method": "hourly_capped"}
// 응답
{"rated_power_mw": 22.5, "method": "hourly_capped", "total_curtailment_mwh": 85.0,
 "total_absorbed_mwh": 60.0, "absorption_rate": 0.7059}
```

`method`는 07장의 두 계산 방식과 1:1 대응:
- `hourly_capped` = ②(정식 채택) = `sum(min(hourly, rated_power_mw))`
- `naive_upper_bound` = ①(단순 상한) = `rated_power_mw * curtailed_hours`

## 모델 성능 (2026-09-23 재학습 기준)

이 수치는 계획서 05장·07장에 정리된 **연구 검증 결과**(다중 지역·다중 방법론 교차검증)와는
학습/평가 조건이 다르다 — 단일 2023년 전체 테스트 구간으로 단순화한 **1차 프로덕션 베이스라인**이다.
풍력 컨버터는 I장 검증 결과를 반영해 3지점(제주184·고산185·성산188) 평균 관측치로 재학습했고,
태양광 컨버터는 일사량 기준 단일 지점(H장 검증)을 그대로 사용한다. 배포 전 재검토가 필요하다.

### 컨버터 (날씨 → 발전량)

| 모델 | corr | NMAE | n_test |
|---|---|---|---|
| 컨버터(태양광, 184) | 0.967 | 29.6% | 8,743 |
| 컨버터(풍력, 184+185+188 평균) | 0.822 | 42.0% | 8,760 |

풍력 단일지점(184) 베이스라인은 같은 조건에서 corr 0.625 / NMAE 63.1% — 3지점 평균이
corr +0.20, NMAE −21.1%p로 I장의 "위치오차 상쇄" 효과를 재현한다.

### 분류기 — isotonic 확률 보정 (2026-09-23)

세 분류기 모두 **isotonic 보정을 적용**하고, `/predict`는 보정 모델만 로드한다. 보정 전 모델을
서빙하는 경로는 없다. RandomForest의 `predict_proba`는 트리 투표 비율이라 확률로 해석하면
편향돼 있고(`class_weight='balanced'`가 더 부풀린다), 제어량 기댓값과 ESS 판단에 확률을 **값**으로
쓰기 때문에 순위뿐 아니라 크기가 맞아야 한다.

**구간 분리** — 보정 데이터는 기저 학습에도 2023 테스트에도 쓰지 않는다.

| 구간 | 기간 | 용도 |
|---|---|---|
| 학습 | 라벨 시작 ~ **2022-07-01** | 기저 RandomForest |
| **보정** | **2022-07-01 ~ 2023-01-01** | isotonic 매핑 전용 (기저 학습 미사용) |
| 테스트 | 2023-01-01 ~ 2024-01-01 | 아래 수치 (양쪽 모두 미사용) |

각 아티팩트 메타데이터의 `calibration_period`에 같은 값이 기록된다.
학습 n: 태양광 6,552(양성 101) / 풍력 13,104(양성 542). 보정 n: 4,416(태양광 양성 20, 풍력 241).

**보정 전 → 보정 후 (2023 테스트, 실측 발전량 입력)**

| 모델 | AUC | PR-AUC | Brier | top5 (상한) | prec@5% |
|---|---|---|---|---|---|
| 태양광 | 0.9646 → 0.9518 | 0.4061 → 0.3141 | 0.0314 → **0.0281** | 0.4929 → 0.5035 (1.000) | 0.3174 → 0.3242 |
| 풍력(수요 미포함) | 0.9517 → 0.9458 | 0.5216 → 0.4368 | 0.0647 → **0.0474** | 0.4298 → 0.3872 (0.778) | 0.5525 → 0.4977 |
| 풍력(수요 포함·정식) | 0.9698 → 0.9678 | 0.7185 → 0.6750 | 0.0314 → 0.0344 | 0.5417 → **0.5506** (0.778) | 0.6963 → **0.7078** |

보정의 대가가 분명하다 — **PR-AUC는 세 모델 모두 떨어진다**(isotonic의 계단 함수가 순위 해상도를
깎는다). Brier는 태양광·풍력(미포함)에서 개선되지만 정식 모델인 풍력(수요 포함)은 오히려
0.0314→0.0344로 나빠졌다. 그럼에도 보정을 채택한 이유는 제어량 총합 추정이 −58.0%에서
−14.1%로 개선되기 때문이다(아래 2단계 추정). 확률을 **순위로만** 쓰는 용도라면 보정 전 모델
(`classifier_*`, 아티팩트로 함께 저장됨)이 더 낫다.

절대 수치가 이전 문서보다 전반적으로 낮은 것은 보정 구간 6개월을 학습에서 뺐기 때문이다
(예: 풍력 수요 포함 AUC는 학습 2022-12까지였을 때 0.9743 → 지금 보정 전 0.9698).

### 서비스 경로 평가 (`evaluate_pipeline.py`) — 보정 모델 기준

| 모델 | PR-AUC 실측 → 컨버터 | top5 실측 → 컨버터 | AUC 실측 → 컨버터 |
|---|---|---|---|
| `classifier_solar_calibrated` | 0.314 → 0.483 (+53.5%) | 0.504 → 0.794 (+57.8%) | 0.952 → 0.903 |
| `classifier_wind_calibrated` | 0.437 → 0.414 (−5.3%) | 0.387 → 0.341 (−11.9%) | 0.946 → 0.942 |
| `classifier_wind_demand_calibrated` | 0.675 → 0.739 (+9.4%) | 0.551 → 0.586 (+6.4%) | 0.968 → 0.973 |

실제 서빙 경로(날씨→컨버터→분류기)가 실측 발전량을 넣은 경우보다 나쁘지 않다는 결론은 유지된다.
컨버터 예측값이 실측보다 평활해서 분류기 입력으로는 노이즈가 적기 때문으로 보인다.

### 제어량 2단계 추정 (풍력, 2023년) — ①보정 분류 → ②조건부 회귀

단일 회귀가 제어량 0인 시간(전체의 94%)에 끌려 −81.7%까지 과소추정하던 문제를 구조로 분리했다.

- **stage1** = `classifier_wind_demand_calibrated` — 위 보정 분류기를 그대로 쓴다.
  `/predict`가 서빙하는 확률과 **같은 모델**이어야 `expected = probability × 조건부`가 성립한다.
- **stage2** = `curtailment_stage2_wind` — 제어 발생 시간만으로 학습한 E[MWh|curtail].
  0인 시간을 보지 않으므로 shrinkage가 없다.

**stage2 입력 발전량 비교 (2023 제어시간 563시간 MAE, MWh)**

| 학습 입력 \ 평가 입력 | 실측 | 컨버터 |
|---|---|---|
| 실측 | 32.85 | 38.51 |
| **컨버터(배포)** | 37.39 | **31.33** |

학습/서빙 입력이 일치할 때가 항상 낫다. `/predict`는 컨버터 예측 발전량을 넣으므로 컨버터
학습본을 배포한다 — 단일 회귀의 제어시간 MAE 42.8 → **31.3 MWh (−27%)**.

**(a) 기댓값(확률 × 조건부) 2023 총합** — 실측 26,197 MWh

| 입력 | 예측 총합 | 오차 |
|---|---|---|
| 실측 발전량 | 16,579 MWh | −36.7% |
| 컨버터 발전량(서빙 경로) | 22,497 MWh | **−14.1%** |

단일 회귀 −81.7% → 보정 전 2단계 −58.0% → **보정 후 −14.1%**. 총합 추정은 실용 수준에 들어왔다.

**(b) 임계값 방식 → `/ess/simulate` hourly_capped (ESS 22.5MW)**

| 시간별 계열 | 제어량 합 | 흡수량 | 흡수율 | 실측 대비 |
|---|---|---|---|---|
| **실측 제어량 (기준)** | 26,197 MWh | 9,632 MWh | **36.8%** | — |
| 임계값 0.07 방식 | 54,599 MWh | 40,290 MWh | 73.8% | **+37.0%p** |
| 기댓값 방식 | 22,497 MWh | 18,135 MWh | 80.6% | +43.8%p |

**총합은 좋아졌지만 ESS 흡수율은 여전히 쓸 수 없다.** 임계값 0.07은 F1 최대 기준이라 탐지에는
맞지만 에너지 회계로는 과다 발동해 제어량 합이 실측의 2.1배가 된다. 기댓값 방식은 총합은
맞지만 확률을 곱해 계열이 평탄해져서 22.5MW 상한에 덜 걸린다. 둘 다 흡수율을 크게 부풀린다.

### 운영 임계값

| 항목 | 값 |
|---|---|
| **운영 임계값** | **0.07** |
| 선정 구간 | 2022-07-01 ~ 2023-01-01 (2023 테스트 미사용) |
| 선정 모델 | 기저 <2022-01-01 + isotonic(2022-01-01~2022-07-01) — 배포 모델에 in-sample이 되지 않도록 한 칸 앞당긴 중첩 분할 |
| 선정 기준 | F1 최대 (F1 0.683 / 정밀도 0.639 / 재현율 0.734) |

> ⚠ **백엔드·대시보드 필독 — 0.5 같은 고정 기준을 쓰지 말 것.**
> isotonic 보정으로 확률의 **크기**가 크게 바뀌었다. 보정 전 0.74였던 시간이 보정 후 0.39로
> 나오는 식이라, 예전 감각으로 만든 임계값(0.5, 0.7 등)을 그대로 쓰면 경보가 거의 울리지 않는다.
> 제어 발생 판정이 필요하면 위 **0.07**을 쓰고, 기준을 바꾸려면 2022 구간에서 다시 고를 것.
> 확률을 등급(낮음/보통/높음)으로 표시할 때도 구간 경계를 재산정해야 한다.

**알려진 한계 (정직하게 기록)**
- 풍력 컨버터(3지점 평균) NMAE 42.0%는 I장의 최종 수치(NMAE 12~15.6%)에 아직 못 미친다 —
  I장은 예보 아카이브의 리드타임별 앙상블까지 반영한 결과이고, 여기서는 ASOS 실측 관측치의
  단순 회귀만 사용하기 때문. 개선 방향(다지점 평균)은 검증됐으나 절대 수치는 추가 작업 필요.
- 풍력 수요피처는 단일 2023년 분할(top5 0.425→0.561)과 6블록 교차검증(0.3767→0.4978, +12.1%p)
  **양쪽 모두에서 일관되게 개선**을 보인다. 수정 전 코드에서 나타났던 "단일 분할 역전"과
  "블록CV 개선폭이 J장의 +11.6%p보다 작음(+1.3%p)"은 둘 다 상한에 막힌 지표가 만든 착시였고,
  라벨 구성을 고친 지금은 J장이 보고한 개선폭(+11.6%p)과 사실상 같은 크기(+12.1%p)가 나온다.
  09장 리스크에서 해제.
- **2단계 + 보정으로 총합은 실용 수준이 됐지만 ESS 흡수율은 여전히 쓸 수 없다.** 총합 오차
  −81.7%→−14.1%, 제어시간 MAE 42.8→31.3MWh로 크게 나아졌다. 그러나 2023 흡수율은 실측 36.8%
  대비 임계값 방식 73.8%(+37.0%p)·기댓값 방식 80.6%(+43.8%p)로 과대평가된다. 원인은 서로 다르다 —
  임계값 0.07은 F1 최대라 탐지에는 맞지만 과다 발동해 제어량 합이 실측의 2.1배가 되고, 기댓값
  방식은 확률을 곱해 계열이 평탄해져 22.5MW 상한에 덜 걸린다. stage2의 분포 압축(실측 평균
  46.5→예측 32.4MWh, 95분위 153→75.5, 최대 217→95.1)이 공통 배경이다.
  **`/ess/simulate`에 모델 예측값을 넣지 말 것** — 스키마 description과 `/predict`의 `note`에도
  같은 경고를 넣어뒀다. 09장 최우선 리스크로 유지한다. 다음 후보: 분위수 회귀나 로그변환으로
  꼬리를 살리기, 임계값 기준을 F1이 아니라 총 제어량 일치로 바꾸기.
- **isotonic 보정은 공짜가 아니다.** PR-AUC가 세 모델 모두 떨어졌고(태양광 0.406→0.314,
  풍력 미포함 0.522→0.437, 풍력 수요포함 0.719→0.675), 정식 모델인 풍력(수요 포함)은 Brier도
  0.0314→0.0344로 나빠졌다. 보정 구간 6개월을 학습에서 뺀 손실까지 겹친다. 총합 추정 개선
  (−58.0%→−14.1%)이 이를 상쇄한다고 판단해 채택했으나, 확률을 순위로만 쓰는 용도라면 함께
  저장된 보정 전 아티팩트(`classifier_*`)가 낫다.
- **태양광 보정 구간의 양성이 20건뿐이다**(2022 하반기). isotonic 매핑이 불안정할 수 있어
  태양광 확률의 크기는 풍력보다 신뢰도가 낮다. 태양광 제어가 2022 상반기에 몰려 있어(98건)
  달리 떼어낼 구간이 없었다 — 2023 데이터가 학습에 편입되면 재검토할 것.
- `validate_demand_blockcv.py`는 보정 없이 자체 학습한 모델로 비교한다 — 수요피처 기여도를 보는
  ablation이라 양쪽 모두 보정 전으로 두는 것이 공정하다. 서빙 모델과는 무관하다.
- 태양광 제어량(MWh)은 전력거래소가 공식 산정하지 않으므로 이 표에 없다(07장) — API 응답에서도
  `expected_curtailment_mwh`는 항상 null이다.

  smoke_test.py             # FastAPI TestClient 기반 엔드투엔드 점검
