# 제주 계통 잉여 위험 예측 AI 서버

계획서(출력제어예측_프로젝트계획서.docx) 02장·04장·06장·07장·09장에서 정의한 AI 서버 구현체.
Backend(Java/Spring Boot)가 REST로 호출하는 내부 서비스다.

> ### 이 서버가 예측하는 것
>
> **시간대별 계통 잉여 위험도** — 재생에너지 발전량이 수요 대비 과다해 출력을 줄여야 할
> 압력이 높은 시간을 가려낸다.
>
> 학습 라벨은 **2024년 5월까지의 강제 출력제어 이력**이다. 2024년 6월 제주 재생에너지
> 입찰제도 전환 이후로는 제어가 계통운영자의 일방적 지시가 아니라 **15분 단위 시장의
> 입찰·낙찰 결과**로 결정되므로, 이 모델의 출력을 "출력제어를 당할 확률"로 읽으면 안 된다.
> 잉여를 만드는 물리적 조건(발전량·수요·기상)은 제도와 무관하게 유지되므로, **어느 시간에
> 잉여 압력이 높은지를 가리는 순위 지표**로 읽어야 한다.
>
> 자세한 배경은 아래 [제도 전환과 예측 대상의 정의](#제도-전환과-예측-대상의-정의)를 볼 것.

## 제도 전환과 예측 대상의 정의

### 무슨 일이 있었나

제주는 **2024년 6월 1일** 전력시장 제도개선 시범사업을 본격 시행했다(2024-03-01~05-31 모의운영).
시범사업은 실시간시장·예비력시장·재생에너지 입찰제도로 구성되며, 재생에너지도 가격을 입찰해
**시장 기반으로 출력 제어량이 결정**되는 구조로 바뀌었다. 실시간시장은 **15분 단위**로 운영된다.

이 전환이 우리 데이터에 그대로 찍혀 있다.

| 데이터 | 마지막 기록 |
|---|---|
| 제주 풍력 출력제어 이력 | **2024-05-30** |
| 제주 태양광 출력제어 이력 | **2024-06-03** |
| 제주 풍력 발전량(전력거래량) | 2024-06부터 정상치의 4~10% 수준으로 급락 |

제어가 가장 활발한 봄철 한가운데서 끊긴다 — 2024년 5월 풍력 82시간·3,568MWh에서 6월 0으로
간다. 제어가 사라진 게 아니라 **기록 체계가 바뀐 것**이다. 전력거래소 비중앙 출력제어 정보
게시판의 2024-06-01 공지가 기전을 직접 보여준다.

> 출력제어 설비용량: 태양광 56.4MW, **풍력(재생에너지 입찰시장 참여로 제어실적 없음)**

제주 풍력은 대부분 3MW를 넘어 입찰 참여가 의무라 먼저 빠졌고, 태양광은 소규모가 많아
한동안 남았다가 2025-05-04 공지를 끝으로 게시가 멈췄다.

### 그래서 예측 대상을 이렇게 정의한다

| | 2024-06 이전 (학습 라벨) | 2024-06 이후 (운영 환경) |
|---|---|---|
| 제어 결정 | 계통운영자의 강제 지시 | 입찰 가격 + 실시간 계통 제약 |
| 라벨 의미 | "제어 명령이 내려졌는가" | "내 입찰이 낙찰되지 않았는가" |
| 시간 해상도 | 1시간 | 15분 |

**같은 이름의 다른 변수다.** 그래서 모델 출력을 "출력제어 확률"이 아니라 **잉여 위험도**로
정의한다. 근거는 두 제도에 공통인 물리다 — 발전량이 많고 수요가 적으면 잉여가 생기고,
그 잉여는 강제 제어로 처리되든 시장 입찰로 처리되든 **누군가의 출력이 줄어든다**.

바뀐 것은 "누가 어떤 절차로 줄이는가"이고, 바뀌지 않은 것은 "언제 줄여야 하는가"다.
이 모델은 후자를 예측한다.

### 읽는 방법

- **순위로 읽을 것.** "내일 13시가 09시보다 잉여 위험이 높다"는 유효하다.
- **절대 확률로 읽지 말 것.** 2026년의 제어 발생 기저율을 알 수 없어 확률의 크기를
  검증할 방법이 없다. 대시보드에는 등급(높음/보통/낮음)으로 노출하는 것을 권장한다.
- **`expected_curtailment_mwh`는 구 제도 기준 추정치다.** 신제도의 15분 단위 제어량과는
  단위도 정의도 다르다. ESS 계산에 쓰지 말 것(아래 경고 참고).

### 한계와 다음 단계

신제도의 제어 실적은 **공개 통계로 나오지 않는다.** EPSIS 전체 메뉴에 출력제어·제주·실시간시장
항목이 없고, 비중앙 출력제어 게시판의 제주 글은 2025-05로 끝난다. 게시되던 값도 제어
**설비용량(MW)**이라 MWh가 아니다.

신제도 데이터를 확보하려면 전력거래소 정보공개청구나 시범사업 참여사업자 경로가 필요하다.
확보 후 15분 단위 라벨로 재학습하는 것이 이 프로젝트의 다음 단계다.

**참고 자료**

**요청**
```json
{
  "energy_type": "solar" | "wind",
  "region": "남원읍",
  "target_date": "2026-09-22",
  "weather": [ {"hour": 1, "solar_rad": 0.0, "temp": 18.2, "cloud": 4.0, "wind_speed": 5.1}, ... 24개 ... ],
  "demand_forecast_mw": [600.1, ...] // 24개, 선택 — 있으면 태양광·풍력 모두 정확도가 올라감
}
```

**검증 책임 분담 (09장 리스크 대응 그대로)**
- Backend: `weather` 필드 존재 여부·JSON 타입만 확인
- AI 서버(여기): `weather`가 정확히 24개인지, 1~24시가 중복·누락 없이 있는지 최종 검증
  - 위반 시 `422 {"error_code": "INVALID_HOUR_SET", "message": "..."}`
- AI 서버(여기): 발전원별 필수 기상값이 24시간 모두 있는지 검증
  - 태양광: `solar_rad`, `temp`, `cloud` / 풍력: `wind_speed`
  - 위반 시 `422 {"error_code": "MISSING_REQUIRED_FIELD", "message": "..."}`
- Backend는 이 에러코드들을 그대로 릴레이하면 됨 (별도 매핑 불필요)

**응답**
```json
{
  "energy_type": "solar",
  "region": "남원읍",
  "target_date": "2026-09-22",
  "hourly": [
    {"hour": 1, "generation_forecast_mwh": 0.0, "curtailment_probability": 0.02, "expected_curtailment_mwh": null},
    ...
  ],
  "model_used": "classifier_solar_demand_calibrated_sigmoid",  // 확률을 산출한 보정 모델
  "note": "태양광은 ... expected_curtailment_mwh를 제공하지 않습니다 ..."  // 태양광, 또는 풍력에서 수요예측 생략 시
}
```

`demand_forecast_mw`를 생략하면 침투율 미포함 모델로 예측하고, 풍력의 경우
`expected_curtailment_mwh`는 null이다(제어량 회귀모델이 수요 피처를 필요로 함).

**중요**: `expected_curtailment_mwh`는 **풍력만** 값이 채워진다. 태양광은 항상 `null`이다 —
전력거래소가 태양광 출력제어량(MWh)을 공식적으로 산정하지 않기 때문(계획서 07장, data.go.kr 메타데이터로
확인됨). 프론트엔드/대시보드에서 태양광에 대해 이 필드를 표시할 때는 반드시 `note` 문구를 함께 노출할 것.

**⚠ ESS 계산에 쓰지 말 것**: `expected_curtailment_mwh`는 `P(제어 발생) × E[제어량|제어 발생]`로
계산한 **기댓값**이다. 총합 추정에는 쓸 수 있으나 개별 시간의 제어량 크기가 아니므로,
`/ess/simulate`의 `hourly_curtailment_mwh`로 그대로 넘기면 흡수율이 크게 과대평가된다
(2023 검증: 실측 36.8% → 80.6%). 자세한 수치는 아래 '제어량 2단계 추정' 및 '알려진 한계' 참고.

### POST /ess/simulate

04장 02번(기본 ESS 시뮬레이션)과 03번(용량 조정 슬라이더)이 공유하는 엔드포인트.

`hourly_curtailment_mwh`에는 **실측 제어량**을 넣는다. `/predict`의 `expected_curtailment_mwh`를
넣으면 안 된다(위 경고 참고).
슬라이더는 `rated_power_mw`만 바꿔가며 이 엔드포인트를 반복 호출하면 된다.

```json
// 요청
{"hourly_curtailment_mwh": [10, 30, 5, 0, 40], "rated_power_mw": 22.5, "method": "hourly_capped"}
// 응답
{"rated_power_mw": 22.5, "method": "hourly_capped", "total_curtailment_mwh": 85.0,
 "total_absorbed_mwh": 60.0, "absorption_rate": 0.7059}
```

`method`는 07장의 두 계산 방식과 1:1 대응:
- `hourly_capped` = ②(정식 채택) = `sum(min(hourly, rated_power_mw))`
- `naive_upper_bound` = ①(단순 상한) = `rated_power_mw * curtailed_hours`

### 데이터 출처 — 두 출처를 섞지 않는 이유 (2026-09-25)

제주 발전량 실적은 성격이 다른 두 데이터셋에서 온다. **모집단이 달라 그대로 이어붙이면 안 된다.**

| | 기존 | 신규 |
|---|---|---|
| 데이터셋 | 제주지역 태양광·풍력 시간대별 발전량 | 지역별 시간별 태양광 및 풍력 발전량 |
| 수록 | 2019-12 ~ 2023-12 | 2024-01 ~ 2025-12 |
| 포맷 | 1시~24시 와이드 | 거래일/거래시간/지역/연료원 롱 |
| 모집단 | 제주 전체 | **전력시장 참여 발전기만** — 한전 직접거래(PPA)·자가용 제외 |
| 기준 | — | 송전단 기준(소내용·주변압기 손실 제외), ESS 충방전량 포함 |

설비는 계속 느는데 출처가 바뀌는 지점에서 총량이 꺾인다.

| 연도 | 출처 | 연 발전량 | 일사량 1MJ/m2당 | 전년비 |
|---|---|---|---|---|
| 2021 | 기존 | 344.4 GWh | 67.79 | — |
| 2022 | 기존 | 407.7 GWh | 79.62 | +17.5% |
| 2023 | 기존 | 487.2 GWh | 99.17 | +24.6% |
| 2024 | **신규** | 448.5 GWh | 97.16 | **−2.0%** |
| 2025 | 신규 | 466.0 GWh | 90.34 | **−7.0%** |

겹치는 구간이 없어 보정계수를 구할 수 없고, 입찰제도 하의 제어 증가와도 섞여 있다.
그래서 **컨버터는 한 출처만 쓴다** — 신규 단독이 혼합보다 학습 데이터가 1/5인데도 정확했다.

| 구성 | 학습 행 | NMAE |
|---|---|---|
| 기존 단독 (2023 테스트) | 17,502 | 25.44% |
| **신규 단독 (2025 테스트, 채택)** | 7,342 | **22.74%** |
| 혼합 (2025 테스트) | 35,043 | 25.09% |

`capacity_factor`는 비율이라 출처 간 배율 차이가 분자·분모에서 상쇄된다. 컨버터와 서빙
대리지표가 **같은 출처**를 쓰면 분류기가 기존 출처로 학습한 관계와 호환된다.
`load_generation_actual(energy_type, source="all"|"legacy"|"market")`로 명시적으로 고른다.

**스키마 변형 주의** — 완전일치로 거르면 한 해가 통째로 조용히 빠진다.

| | 2024년판 | 2025년판 |
|---|---|---|
| 날짜 컬럼 | `거래일자` | `거래일` |
| 지역 표기(태양광) | `제주도` | `제주도` |
| 지역 표기(풍력) | **`제주`** | `제주도` |

**풍력은 2024-06-01이 상한이다.** 입찰제도 본격 운영과 함께 이 데이터셋에서 사실상 사라진다 —
발전을 안 한 게 아니라 거래가 다른 경로로 정산되는 것으로 보인다.

| 지표 | 2023 | 2024 | 2025 |
|---|---|---|---|
| 5월 월합계 | 정상 | 42,657 → 6월 **5,421** MWh | 2,554 MWh |
| 풍속 상관 | 0.786 | 0.624 | 0.540 |
| 평균 발전량 | 58.1 MWh | 42.1 | **8.6** |

이 구간을 학습에 넣으면 컨버터가 "바람이 불어도 발전하지 않는다"를 학습한다.
`data_prep.GENERATION_VALID_END`가 자동으로 잘라낸다.

### 입력 정규화 — 설비 증설 대응 (2026-09-25)

제주 태양광 설비가 계속 늘어 **발전량 절대값(MWh)의 분포가 해마다 위로 밀린다.**
정오대(11~14시) 평균이 2021년 123 → 2022년 149 → 2023년 178MWh, 연간 최대가
214 → 269 → 336MWh다. RandomForest는 외삽을 못 하므로 학습 범위를 벗어난 입력에서
경계에 포화되고, 큰 발전량 시간들이 서로 구분되지 않아 순위가 무너진다.

그래서 발전량 절대값을 두 개의 **스케일 안정 피처**로 대체했다.

    capacity_factor = 발전량 / 설비용량 대리지표   -> 날씨 강도. 증설과 무관하게 [0,1] 근처
    penetration     = 발전량 / 수요                -> 잉여 압력. 출력제어의 실제 구동 요인

이용률만 쓰면 '잉여 규모' 정보를 잃고, 절대 MWh만 쓰면 범위를 벗어난다. 둘 다 필요하다.

**설비용량 대리지표** — 공개된 설비용량 시계열이 없어 발전량 이력에서 만든다.
과거 365일의 99분위수(태양광은 사실상 '맑은 날 정오 최대 출력')를 쓰고, `shift(1)`로
현재 시각을 제외해 **인과성**을 지킨다. 발전량 실적은 2019-12부터, 라벨은 2021-01부터라
라벨 시작 시점에 이미 13개월 이력이 쌓여 있어 학습 데이터 손실이 없다.

연도별 대리지표(중앙값): 태양광 215 → 217 → 232 → 286 → 295 MWh (증설),
풍력 234 → 210 → 215 → 214 → 216 MWh (거의 평평).

**피처 구성 비교 (2023 테스트, 보정 전 기준)** — `models/normalization_experiment.csv`

| 구성 | 태양광 PR-AUC | 태양광 top5 | 학습범위 밖 | 풍력 PR-AUC |
|---|---|---|---|---|
| A 현행(절대 MWh) | 0.4061 | 0.4929 | **3.76%** | 0.7185 |
| B 이용률 | 0.6386 | 0.8085 | 0.14% | 0.7233 |
| **C 이용률+침투율 (채택)** | **0.7032** | **0.8262** | 0.14% | **0.7312** |
| D 전부(절대 MWh 포함) | 0.6291 | 0.7908 | 3.76% | 0.7171 |

태양광은 **PR-AUC +73%, top5 +68%**다. 풍력은 +1.8%로 사실상 변화가 없는데, 이는 실패가
아니라 **진단의 확인**이다 — 풍력은 증설이 없어 학습범위 밖 비율이 원래 0.11%였고,
고칠 문제 자체가 없었다. **정규화 효과가 증설이 일어난 곳에만 나타난다.**

D(절대 MWh를 함께 넣기)가 C보다 나쁜 점에 주의할 것. 안전해 보이지만 RandomForest가
절대값 쪽으로 분기를 만들어 포화 문제를 도로 끌고 들어온다. **절대 발전량은 빼야 한다.**

### 컨버터 (날씨 → 발전량)

컨버터는 문제의 방향이 반대다 — 입력(날씨)은 드리프트하지 않고 **타깃**인 발전량이 커진다.
그래서 발전원별로 타깃을 다르게 쓴다.

| 모델 | 타깃 | 출처 | 테스트 | corr | NMAE |
|---|---|---|---|---|---|
| 컨버터(태양광, 184) | **capacity_factor** | 신규 | 2025년 | 0.9522 | **22.74%** |
| 컨버터(풍력, 184+185+188) | generation_mwh | 기존+신규 | 2023년 | 0.8217 | 42.04% |

발전원별로 출처와 테스트 구간이 다르다 — 쓸 수 있는 범위가 다르기 때문이다(위 '데이터 출처').
아래 A/B1/B2 비교는 기존 출처·2023 테스트 기준이며, 신규 단독으로 바꾼 현재는 22.74%다.

**태양광 타깃 정규화 비교** — `models/converter_normalization_experiment.csv`
(학습 타깃 최대 269MWh, 2023 실측 최대 336MWh)

| 변형 | corr | NMAE | 예측 최대 | 서빙 가능 |
|---|---|---|---|---|
| A 현행(MWh 타깃) | 0.9675 | 29.63% | 251MWh | ✅ |
| B1 이용률 타깃 / 시점별 대리 | 0.9684 | 19.93% | 303MWh | ❌ 미래 대리지표 필요 |
| **B2 이용률 타깃 / 고정 대리 (채택)** | 0.9667 | **25.44%** | 280MWh | ✅ |

A는 예측 최대가 251MWh로 **학습 최대 269를 단 한 번도 넘지 못한다** — 외삽 실패가 눈에 보인다.
B는 280~303MWh까지 예측한다. B1이 가장 좋지만 미래 시각의 대리지표를 알 수 없어 서빙에는
쓸 수 없고, `/predict`가 실제로 하는 것은 B2다. **B1과 B2의 격차(19.9% vs 25.4%)가
재학습 주기의 비용**이며, 연 1회 이상 재학습을 권고하는 정량적 근거다.

풍력은 정규화해도 42.04% → 42.06%로 변화가 없다. 2023 실측이 학습 최대를 넘는 시간이
0.03%(3시간)뿐이라 외삽할 일이 없었다. 풍력 오차의 원인은 외삽이 아니라 **관측지점과
풍력단지의 위치 불일치**이고, 3지점 평균으로 이미 대응한 부분이다.
(단일지점 baseline: corr 0.625 / NMAE 63.1%)

> **설비용량 대리지표의 정합성**: 컨버터가 곱하는 상수와 분류기가 나누는 상수는 **반드시 같아야**
> 왕복이 상쇄된다. 양쪽 모두 `data_prep.latest_capacity_proxy()`로 계산해 아티팩트
> 메타데이터 `capacity_proxy_mwh`에 저장하며, 현재 값은 **295.11MWh**다.
> 컨버터 NMAE를 낼 때는 학습 시점에 알 수 있었던 값(242.15MWh)을 따로 써서 미래 정보가
> 섞이지 않게 한다(`eval_capacity_proxy_mwh`).

### 분류기 — 확률 보정 (sigmoid 서빙)

세 발전원·수요 조합 **네 모델** 모두 isotonic·sigmoid 두 방식으로 보정해 저장하고,
`/predict`는 **sigmoid 보정본**만 로드한다. 보정 전 모델을 서빙하는 경로는 없다.

**구간 분리** — 보정 데이터는 기저 학습에도 2023 테스트에도 쓰지 않는다.

| 구간 | 기간 | 용도 |
|---|---|---|
| 학습 | 라벨 시작 ~ **2022-07-01** | 기저 RandomForest |
| **보정** | **2022-07-01 ~ 2023-01-01** | 보정 매핑 전용 |
| 테스트 | 2023-01-01 ~ 2024-01-01 | 아래 수치 |

학습 n: 태양광 6,552(양성 101) / 풍력 13,104(양성 542). 보정 n: 4,416(태양광 양성 20, 풍력 241).

**2023 테스트, 실측 발전량 입력 (보정 전 → isotonic → sigmoid(서빙))**

| 모델 | AUC | PR-AUC | Brier | top5 (상한) | prec@5% |
|---|---|---|---|---|---|
| 태양광 | 0.9809 → 0.9659 → **0.9809** | 0.6386 → 0.4756 → **0.6386** | 0.0236 → 0.0250 → **0.0188** | 0.8085 → 0.7872 → 0.8085 (1.000) | 0.5205 |
| 태양광+수요 | 0.9882 → 0.9687 → **0.9882** | 0.7105 → 0.5889 → **0.7105** | 0.0172 → **0.0164** → 0.0183 | 0.8475 → 0.8227 → 0.8475 (1.000) | 0.5457 |
| 풍력 | 0.9513 → 0.9463 → **0.9513** | 0.5147 → 0.4395 → **0.5147** | 0.0649 → **0.0463** → 0.0558 | 0.4298 → 0.3783 → 0.4298 (0.778) | 0.5525 |
| 풍력+수요(정식) | 0.9702 → 0.9679 → **0.9702** | 0.7173 → 0.6795 → **0.7173** | **0.0317** → 0.0324 → 0.0332 | 0.5471 → 0.5400 → 0.5471 (0.778) | 0.7032 |

sigmoid는 단조 변환이라 **순위 지표를 보정 전과 완전히 동일하게 보존**한다. isotonic은
계단함수라 PR-AUC를 최대 −26% 깎는다(태양광 0.6386→0.4756). 확률의 주 용도가 경보·순위
선별이라 sigmoid를 채택했다. isotonic 아티팩트(`classifier_*_calibrated_isotonic`)도 함께
저장되므로 총합 정확도가 더 중요해지면 교체만 하면 된다.

> 컨버터가 학습 범위 밖으로 외삽하지 못해 발전량을 옛 범위로 눌러 출력했고, 그 눌린 값이
> 같은 옛 범위로 학습된 분류기의 분포와 우연히 맞아떨어진 것이었다(2023 실측은 학습 최대
> 263MWh를 329시간 초과했으나 컨버터 예측은 0시간). **실력이 아니라 두 모델이 같은 방향으로
> 틀린 결과였다.** 정규화 후에는 −1~4%로, 예측값 입력이 실측보다 약간 나쁜 정상적인
> 관계로 돌아왔다. 풍력 수요 모델의 +10%는 컨버터 예측값이 더 평활해 분류기 입력으로는
> 노이즈가 적기 때문으로, 이쪽은 실제 효과로 보인다.

### 풍력 수요피처 6블록 교차검증 (`validate_demand_blockcv.py`, 21.01~24.01)

| 지표(양성 가중평균) | 수요 미포함 | 수요 포함 | 변화 |

22.5MW 상한에 덜 걸려 흡수율이 부풀려진다. **해결은 임계값이 아니라 조건부 분포의 꼬리를
살리는 쪽**(분위수 회귀, 로그변환 타깃, 또는 꼬리 전용 모델)에 있다.

### 분포 적분 방식 — ESS 흡수율

임계값 방식이 실패한 근본 원인은 **점 예측으로는 `min()`을 적분할 수 없다**는 것이다.
ESS 흡수량은 `sum(min(제어량, cap))`이고 `min()`은 비선형이라
`E[min(X, cap)] ≠ min(E[X], cap)`다. 조건부 평균 하나만 예측하면 꼬리가 눌려
상한에 덜 걸리고 흡수율이 부풀려진다. 그래서 시간별로 **분포**를 만들고 그 위에서 적분한다.

    시간별 총 제어량 = Σ P(curtail) × E[X]
    시간별 흡수량    = Σ P(curtail) × E[min(X, cap)]
    흡수율           = 흡수량 / 총 제어량

`P(curtail)`은 보정 분류기(`classifier_wind_demand_calibrated_sigmoid`) 확률이다.

**두 가지 분포 생성 방식**

- **분위수 방식** (`curtailment_stage2_quantile_wind`) — `HistGradientBoostingRegressor
  (loss="quantile")`로 분위수 0.05~0.95를 0.05 간격 19개 학습. 분위수별 독립 학습이라
  역전(crossing)이 생길 수 있어 예측 후 시간별로 정렬해 단조성을 강제한다.
  학습은 2021~2022 제어 발생 시간, 하이퍼파라미터는 2022를 검증셋으로 평균 pinball loss 최소
  기준 선택 → `max_depth=6, learning_rate=0.03, max_iter=800, min_samples_leaf=40`.
- **잔차 방식** — 기존 조건부 회귀(RF 평균)에 2022 경험적 잔차를 더해 분포를 만든다.
  잔차는 out-of-sample이어야 퍼짐이 과소평가되지 않으므로 2021만으로 학습한 모델로 뽑았다
  (n=515, 평균 +19.1MWh, 표준편차 46.4). **중심화**는 그 평균을 빼서 수준 편향을 제거한 변형이다 —
  퍼짐만 빌려오고 수준은 배포 모델 예측을 따른다.

**② 분위수 커버리지 (2023 제어 발생 563시간, '실측 ≤ 예측' 비율)**

| 명목 | 0.05 | 0.15 | 0.25 | 0.35 | 0.45 | 0.55 | 0.65 | 0.75 | 0.85 | 0.95 |
|---|---|---|---|---|---|---|---|---|---|---|
| 실측 | 0.08 | 0.12 | 0.17 | 0.21 | 0.28 | 0.35 | 0.42 | 0.53 | 0.63 | 0.75 |
| 격차 | +3%p | −3%p | −8%p | −14%p | −17%p | −20%p | −23%p | −22%p | −22%p | −20%p |

**분위수 앙상블은 심하게 과소분산(under-dispersed)이다.** 하위 분위수는 맞지만 위로 갈수록
격차가 −23%p까지 벌어진다 — 예측 분포의 폭이 실제보다 훨씬 좁다는 뜻이다. 연도별 분포 변화
때문이 아니다: 제어 발생 시간의 제어량은 2021/2022/2023이 평균 44.8/49.8/46.5MWh,
p95 149/147/153MWh로 안정적이다. 주어진 피처(발전량·시각·월·수요)로는 **어느 시간이 극단적으로
큰 제어량을 갖는지 구분되지 않아** 조건부 분위수가 중앙으로 수축한 것이다.

비율에서만 오차가 상쇄된 것이다. 분위수 방식은 과소분산 탓에 모든 cap에서 +17~19%p 빗나간다.

> ### ⚠ 이 방식의 지위: **연구 검증 (프로덕션 미채택)**
>
> 수치는 좋지만 아래 두 가지 때문에 대시보드에 바로 넣지 않는다.
>
> 1. **잔차 중심화는 사후(post-hoc) 선택이다.** 원래 설계는 잔차 원본이었고, 2023 결과에서
>    총 제어량이 크게 부풀려진 것을 **보고 나서** 중심화를 도입했다. 중심화 자체에는 원리적
>    근거가 있지만(잔차를 뽑은 2021 모델이 배포 모델보다 약해 평균이 +19.1MWh로 치우침),
>    **2023을 보고 고른 이상 2023 수치는 이 선택에 대해 편향돼 있다.** 잔차가 2022에서 나오므로
>    2022로는 검증할 수 없다 — 독립된 연도(2024 이후 실적)가 있어야 한다.
> 2. **단일 연도·3개 cap에서만 측정됐다.** 잔차가 피처와 무관하다(등분산)는 가정 위에 있고,
>    실제로는 발전량이 클수록 분산도 클 가능성이 있어 극단 구간에서 오차가 커질 수 있다.
>
> **프로덕션 전환 조건**: 2024년 실적으로 중심화를 포함한 전체 절차를 사전 고정한 뒤 재검증해
> 흡수율 오차가 ±5%p 안에 들 것. 그때까지 대시보드의 ESS 계산은 **실측 제어량 기반만** 사용한다.
>
> 어느 경우든 지켜야 할 것 —
> - **시간별 값은 믿을 수 없다.** 맞는 것은 연 단위 집계(흡수율·총량)뿐이다.
>   "이 시간에 몇 MWh가 흡수된다"는 식의 표시는 하지 말 것.
> - `/predict`의 `expected_curtailment_mwh`를 `/ess/simulate`에 넣는 경로는 **여전히 금지**다
>   (그것은 점 예측이라 분포 적분이 아니다).
>
> **평가 입력 조건(중요)**: 위 흡수율·커버리지 수치는 모두 **ASOS 실측 관측치**와 **실측 전력수요**를
> 입력으로 얻은 값이다. 실제 운영은 기상 **예보**와 **수요예측**을 넣으므로 추가 오차가 얹힌다 —
> 이 표는 운영 성능이 아니라 **상한**으로 읽어야 한다. (컨버터 예측 발전량을 쓴다는 점만 서빙과
> 같다.) 하루전 예보 아카이브가 이 저장소에 없어 예보 입력 평가는 불가능하다.

선정 모델은 배포 모델과 **같은 보정 방식**이어야 임계값이 같은 확률 척도 위에 놓인다.
배포 모델에 in-sample이 되지 않도록 한 칸 앞당긴 중첩 분할을 쓴다.
전체 격자는 `models/curtailment_threshold_grid.csv`에 저장된다.

> ⚠ **보정 방식을 바꾸면 임계값도 반드시 다시 골라야 한다.** isotonic일 때 0.07이던 값이
> sigmoid에서는 0.03이다. 확률 척도가 달라지기 때문이며, 옛 임계값을 그대로 쓰면 발동 빈도가
> 크게 달라진다.

> ⚠ **백엔드·대시보드 필독 — 0.5 같은 고정 기준을 쓰지 말 것.**
> 보정으로 확률의 **크기**가 바뀌었다. 방향이 한쪽이 아니라 구간마다 다르다 — 낮은 쪽은 더
> 낮아지고 높은 쪽은 더 높아진다(2023 풍력+수요 기준).
>
> | 분위수 | 보정 전 | isotonic | **sigmoid(서빙)** |
> |---|---|---|---|
> | p75 | 0.043 | 0.020 | 0.020 |
> | p90 | 0.239 | 0.500 | 0.181 |
> | p95 | 0.418 | 0.676 | 0.656 |
> | p99 | 0.892 | 1.000 | 0.998 |
>
> 예: 보정 전 0.700이던 시간은 sigmoid(서빙)에서 0.983이 된다 — 크게 올라간다.
> 예전 감각으로 만든 임계값이나 등급 구간(낮음/보통/높음)을 그대로 쓰면 발동 빈도가 의도와
> 달라진다. 제어 발생 판정이 필요하면 위 **0.03**을 쓰고, 기준을 바꾸려면 2022 구간에서 다시
> 고를 것(현재 **0.03**). 확률 크기에 의존하는 표시는 모델을 재학습하거나 보정 방식을
> 바꿀 때마다 재산정해야 한다.

**알려진 한계 (정직하게 기록)**
- 풍력 컨버터(3지점 평균) NMAE 42.0%는 I장의 최종 수치(NMAE 12~15.6%)에 아직 못 미친다 —
  I장은 예보 아카이브의 리드타임별 앙상블까지 반영한 결과이고, 여기서는 ASOS 실측 관측치의
  단순 회귀만 사용하기 때문. 개선 방향(다지점 평균)은 검증됐으나 절대 수치는 추가 작업 필요.
- 풍력 수요피처는 단일 2023년 분할(top5 0.425→0.561)과 6블록 교차검증(0.3767→0.4978, +12.1%p)
  **양쪽 모두에서 일관되게 개선**을 보인다. 수정 전 코드에서 나타났던 "단일 분할 역전"과
  "블록CV 개선폭이 J장의 +11.6%p보다 작음(+1.3%p)"은 둘 다 상한에 막힌 지표가 만든 착시였고,
  라벨 구성을 고친 지금은 J장이 보고한 개선폭(+11.6%p)과 사실상 같은 크기(+12.1%p)가 나온다.
  09장 리스크에서 해제.
- **[최우선] 학습 라벨과 운영 환경의 제도가 다르다.** 라벨은 2024년 5월까지의 강제 출력제어
  이력이고, 2024-06부터 제주는 15분 단위 시장의 입찰·낙찰로 제어량이 결정된다. 예측 대상을
  '출력제어 확률'이 아니라 **잉여 위험도**로 정의하고 순위 지표로만 쓰는 것이 이 한계에 대한
  대응이다(위 '제도 전환과 예측 대상의 정의'). **2026년 정확도를 측정할 방법이 없다** —
  신제도 라벨이 공개되지 않아 검증 자체가 불가능하다. 절대 확률 노출을 피하고 등급으로
  표시할 것을 권장하는 이유다. 신제도 라벨 확보 후 15분 단위 재학습이 다음 단계다.
- **[신규] 발전량 데이터 출처가 2024년부터 바뀌었고 모집단이 다르다.** 신규 데이터셋은
  전력시장 참여 발전기만 담아 한전 직접거래(PPA)·자가용을 제외한다. 그 결과 설비가 느는데도
  연 총합이 2023년 487.2GWh → 2024년 448.5GWh로 8% 줄고, 일사량당 발전량 증가율이
  +24.6% → −2.0%로 꺾인다. 겹치는 구간이 없어 보정계수를 구할 수 없으므로 **컨버터는
  한 출처만 쓴다**(위 '데이터 출처'). `capacity_factor`가 비율이라 배율 차이는 상쇄되지만,
  **API 응답의 `generation_forecast_mwh`는 절대값이라 과소 추정될 수 있다.**
- **설비용량 대리지표는 엄밀히 '기록된 최대 출력'이다.** 신규 출처 기준으로 2024년 말
  320MWh → 2025년 말 281MWh로 내려갔는데, 설비가 줄어서가 아니라 입찰제도 하의 제어로
  기록상 최대 출력이 눌린 것이다. 분류 성능에는 영향이 없으나(분자·분모에서 상쇄),
  절대 발전량 표시에는 영향이 있다. 공개 설비용량 시계열을 확보하면 대체할 것.
- **풍력 발전량은 2024-06-01이 상한이다.** 입찰제도 전환으로 이 데이터셋에서 사라진다
  (평균 58.1 → 8.6MWh, 풍속 상관 0.786 → 0.540). 출력제어 이력이 2024-05에서 끊긴 것과
  같은 원인이며, 풍력 컨버터·분류기의 데이터 상한이 된다.
- **[대응 완료] 태양광 '컨버터 입력이 실측보다 낫다'는 결과는 설비 증설이 만든 착시였다.**
  `evaluate_pipeline`에서 태양광 PR-AUC가 실측 입력 0.314 → 컨버터 입력 0.483(+53.5%)으로
  올라가는데, 원인을 확인한 결과 **분포 이동**이었다. 제주 태양광 실측 발전량은 정오대(11~14시)
  평균이 2021년 123 → 2022년 149 → 2023년 178MWh, 연간 최대가 214 → 269 → 336MWh로 계속
  커진다(설비 증설). 분류기 학습 구간(<2022-07-01)의 최대는 263MWh인데, **2023 실측은 이를
  329시간(3.8%) 초과**한다. 반면 **컨버터 예측은 2023에 단 한 시간도 263을 넘지 않는다**
  (최대 250MWh) — 컨버터 역시 학습 범위 밖으로 외삽하지 못해 발전량을 옛 범위로 눌러 출력하기
  때문이다. 그 눌린 값이 분류기가 학습한 분포와 우연히 맞아떨어져 성능이 좋아 보이는 것이다.
  **실력이 아니라 두 모델이 같은 방향으로 틀린 결과다.**
  **대응(2026-09-25 적용)**: 발전량을 절대값이 아니라 이용률·침투율로 정규화하고, 태양광
  컨버터는 타깃 자체를 이용률로 바꿨다. 착시가 사라져 서비스 경로가 +70% → **−11%**로,
  예측값 입력이 실측보다 약간 나쁜 정상적인 관계로 돌아왔다. 동시에 태양광 분류기 PR-AUC가
  0.406 → 0.711로, 컨버터 NMAE가 29.6% → 25.4%로 개선됐다(위 '입력 정규화' 절).
  **다만 근본 해소는 아니다** — 설비용량 대리지표가 학습 시점 값으로 고정되므로 증설이 이어지면
  실제와 벌어진다. B1(시점별 대리, NMAE 19.9%)과 B2(고정, 25.4%)의 격차가 그 비용이며,
  **연 1회 이상 재학습**이 필요하다. 풍력은 증설이 없어 정규화 효과도 없었다(42.04%→42.06%).
- **ESS 흡수율은 점 예측·임계값으로는 불가능하고, 분포 적분으로 풀린다.** 임계값 기준을
  F1에서 총 제어량 일치로 바꿔도 개선되지 않았고(74.5%→81.8%, 실측 36.8%), 2023을 보고 고른
  오라클 임계값(0.17)조차 68.0%였다 — 임계값 탐색의 상한 자체가 부족하다. 원인은
  `E[min(X,cap)] ≠ min(E[X],cap)`인데 점 예측으로 `min()`을 계산했기 때문이다. 시간별 분포를
  만들어 적분하는 **잔차(중심화) 방식**은 cap 22.5/30/40MW에서 오차 −0.45/+0.41/+1.48%p,
  총 제어량 −4.9%로 ±5%p 기준을 통과한다. **다만 프로덕션에는 채택하지 않았다** — 중심화가
  2023 결과를 보고 고른 사후 선택이라 이 수치는 그 선택에 대해 편향돼 있고, 단일 연도·3개 cap
  에서만 측정됐다. 현재 지위는 **연구 검증**이고, 대시보드의 ESS 계산은 2024년 실적으로
  재검증하기 전까지 **실측 제어량 기반만** 쓴다. 연 단위 집계만 의미가 있고 시간별 값은 여전히
  못 쓴다 — 위 '분포 적분 방식' 절의 조건을 지킬 것.
- **분위수 회귀는 이 문제에서 실패했다.** 분위수 19개(0.05~0.95)를 학습했지만 2023 커버리지가
  명목 대비 최대 −23%p로 심하게 과소분산이라 흡수율이 +17~19%p 빗나간다. 연도별 분포 변화가
  아니라(2021~2023 조건부 평균 44.8/49.8/46.5MWh로 안정) 피처가 제어량의 크기를 설명하지
  못해 조건부 분위수가 중앙으로 수축한 탓이다. 아티팩트
  (`curtailment_stage2_quantile_wind`)는 재현·비교용으로 남겨두되 서비스에는 쓰지 않는다.
  개선하려면 제어량 크기를 설명할 피처(계통 제약, 연계선 조류, 타 발전원 출력 등)가 필요하다.
- **보정 방식은 sigmoid를 채택했다.** isotonic은 PR-AUC를 크게 깎는다(태양광 0.639→0.476,
  태양광+수요 0.711→0.589, 풍력 0.515→0.440, 풍력+수요 0.717→0.680). sigmoid는 단조 변환이라
  순위 지표를 보정 전과 동일하게 보존하면서 Brier를 네 모델 중 둘에서 개선한다. 확률의 주 용도가
  경보·순위 선별이라 이쪽을 택했다. 총합 정확도가 더 중요해지면
  `classifier_*_calibrated_isotonic`으로 교체하면 된다.
- **태양광 보정 구간의 양성이 20건뿐이다**(2022 하반기). 보정 매핑이 불안정할 수 있어
  태양광 확률의 크기는 풍력보다 신뢰도가 낮다(특히 isotonic). sigmoid는 파라미터 2개뿐이라
  이런 소표본에서 상대적으로 안전하다 — 태양광 Brier가 0.0281(isotonic) vs 0.0263(sigmoid)인 것도
  같은 이유로 보인다. 태양광 제어가 2022 상반기에 몰려 있어(98건)
  달리 떼어낼 구간이 없었다 — 2023 데이터가 학습에 편입되면 재검토할 것.
- `validate_demand_blockcv.py`는 보정 없이 자체 학습한 모델로 비교한다 — 수요피처 기여도를 보는
  ablation이라 양쪽 모두 보정 전으로 두는 것이 공정하다. 서빙 모델과는 무관하다.
- 태양광 제어량(MWh)은 전력거래소가 공식 산정하지 않으므로 이 표에 없다(07장) — API 응답에서도
  `expected_curtailment_mwh`는 항상 null이다.
